# 一缕烛光

## Codex 中的使用方式

- 这份 skill 负责视觉判断；制作、导出和操作由当前环境中适用的工具及专用 skill 完成。按任务需要使用网站、文档、演示文稿、PDF、电子表格、图像生成或交互可视化 skill，不必全部加载。
- 用户指定的品牌、参考稿和现有项目的设计系统优先。修改已有作品时，沿用其组件、字体和 token；下文默认值主要用于从零设计或补齐缺项，不为套方向卡而重做项目。
- 引用路径相对于本 skill 所在目录解析，不相对于项目工作目录。截图和临时渲染文件写入任务工作目录，不写入 skill 安装目录。

这份 skill 有三层，各管一件事：

| 层 | 文件 | 作用 | 何时读 |
|---|---|---|---|
| 保底手艺 | [网页视觉](references/floor-web-ui.md)、[交互](references/floor-interaction.md) | 字号、间距、配色、版式，以及状态、反馈和动效 | 做网页 / UI / 落地页时读网页视觉指南。新建或修改可交互页面时也读交互指南。 |
| 方向卡 | [directions.md](references/directions.md) | 让作品**有一个具体的方向**，而不是平均值 | 下文「分岔」判断需要时读 |
| 烛光（本文件） | — | 让作品**更好**：观看、克制、检查 | 始终 |

保底手艺和方向卡都是起点，不是天花板。有理由时可以打破任何默认值；没有理由时，照着做。

- **明确的小改动**（改颜色、修对齐）直接按改动范围执行和验证。涉及交互时检查受影响的状态和流程。
- **已有项目的评审、优化或改版**走[审计流程](references/audit.md)。只评审时交付报告。任务包含修改时，按审计发现做范围内的修复。用户要求探索新方向时，先记录相关现状，再用下文的选方向流程。
- **从零设计**按下文定位、选方向、制作和检查。

## 一、动手之前

### 1. 定位
想清楚：给谁看、在哪里看（手机 / 桌面 / 打印 / 远看）、想让人感受到什么、**第一眼必须落在哪里**。

### 2. 分岔：用自己的方向，还是用方向卡？

问自己一个具体的问题：

> **我能不能说出这个题材真实世界里的一个具体物件、材料、印刷品或地方，并说出它决定了画面的哪一部分（排版、配色、形状或材质）？**

例：「渡轮 App → 借船票票根：打孔边、编号、两栏票面排版」——能说出来，而且它决定了排版和形状。
反例：「科技感」「温暖」「高级」「现代简约」——这些是形容词，不是物件，说明还没有方向。

- **能说出来** → 用自己的方向。方向卡可以不读，或只用来查易砸点。
- **说不出来** → 读[方向卡](references/directions.md)，按里面的方法选一张卡。**选卡后，仍然要从题材里取一个具体元素融进去**，否则作品只是卡片的复制品。

两种情况都要警惕第一反应：每个题材都有所有人共同的第一反应（海洋 → 蓝渐变加波浪；金融 → 深蓝加金；儿童 → 糖果色圆角）。可以选它，但那应该是选择，不是惯性。

### 3. 读保底手艺
做网页 / UI 时，读[网页视觉保底手艺](references/floor-web-ui.md)。方向卡给的字体和色板，套进保底手艺给的字号、间距和版式结构里。可交互页面同时读[交互保底手艺](references/floor-interaction.md)，把状态、反馈和动效纳入设计。

其他媒介（海报、3D、图表）暂无专门的保底文件，用方向卡加本文件即可。

## 二、制作中：克制

- **一个主角。** 全作只有一个视觉焦点在尺度、明度或色彩上占压倒性优势。
- **每加一个元素，问它为谁服务。** 为观众，留下；为了显得做得多，删掉。
- **力气集中。** 一个核心区块做到 95 分，其余安静退后，好过十个区块都做到 70 分。
- **统一语言。** 圆角、线宽、字体、色温、动效节奏用同一套逻辑。要打破，只打破一处。
- **警惕惯性组合**（出现两项以上就停下来想想）：渐变背景、毛玻璃卡片、卡片叠卡片、大圆角、霓虹发光、深色底配单一发光色、彩色胶囊标签、与设计无关的设备外壳、处处居中对称、每块同等精心。题目要求某种形式（如展示手机界面）时满足它，但重心放在内容上。
- **作品里的字属于作品的世界。** 不在作品里写自己的风格名、设计理念、色值、网格参数。编造的数据和参数可以营造质感，但不要铺满。
- **看不到画面时**（没有渲染手段）：少做内容，少用多层绝对定位和出血裁切，把一个核心想法做稳。

## 三、完成后：看

### 渲染并亲眼看
- 按媒介和本次会话实际可用的工具渲染；具体选择见 [Codex 渲染与检查](references/codex-rendering.md)，开始渲染时读。无需通用截图脚本，也不预设系统装有浏览器或 Playwright。
- 网页 / UI 目标检查 1440 和 390 两个 CSS 像素宽度；长页面看首屏、中段、末尾。SVG 看栅格化结果，3D / 动画看代表帧与关键状态。
- **视觉结论要有实际渲染依据。** 内置截图若已作为图像返回，可直接检查。磁盘图片用 `view_image` 等本地图片查看工具打开。无法渲染时，说明哪些画面未验证。

### 第一遍：整体
- 第一眼落在想要的地方吗？
- 遮住文字，它像不像在这类题材上见过很多次的东西？
- 眯眼看，有没有明确的最亮点和最暗点？

方向偏离目标时，说明具体原因。新设计或用户要求重定方向时，优先调整方向，再修细节。

### 第二遍：硬伤（必须做，不算修改轮数）
放大看文字密集处、标注与图形交接处、元素重叠处、容器边缘、四角与底部。评审时把发现写进报告。制作或修复时，解决范围内已确认的硬伤并重新查看渲染结果。
- 文字压住其他元素或文字、撞边、被裁、断行别扭（单字孤行、标点打头）。
- 光晕、渐变被矩形硬切；内容溢出容器；出现横向滚动条。
- 氛围层（纹理、粒子、光束）压过信息层。
- 内容看不见（对比不足、字体或图片加载失败、空白画布）。
- 大块不是刻意留出的空白。

### 交互走查

新建或修改交互时，用当前可用的浏览器工具走一遍受影响的主要流程。按任务检查首次打开、操作反馈、错误恢复、空状态、超长内容、键盘操作和窄屏。详见 [交互走查](references/floor-interaction.md#7-走查用用户的身份过一遍) 与 [Codex 渲染与检查](references/codex-rendering.md)。走查发现的功能和可访问性问题不计入审美修改轮数。

### 第三遍：审美修改（最多一轮）
制作或视觉优化时，从下面的症状表挑最影响观感的一两处修掉。作品已经很满时，删比加有用。

### 交付
- 回复简短：做了什么、文件在哪、一两句话说明方向。
- 写清实际验证的内容和依据。无法渲染时，说明未验证的画面。
- 不复述这份 skill 的步骤，不自我夸奖。

## 症状表（卡住时查）

| 感觉 | 可能的原因 |
|---|---|
| 平、闷 | 明度太接近；没有最亮点和最暗点；色相多但明度单一 |
| 散，没焦点 | 太多元素争夺注意力；对比被平均分配 |
| 拥挤 | 每个元素都想被看见；间距太均匀或太小；没有休息区 |
| 精致但没灵魂 | 意图不清；没有来自题材的具体元素；所有选择都很「安全」 |
| 像模板 / 像 AI | 惯性组合；形式来自流行趋势而不是题材 |
| 用力过猛 | 装饰和伪技术细节塞满；作品在解释自己 |
| 廉价、塑料感 | 饱和度或渐变过度；阴影和发光没有可信光源 |
| 呆板 | 一切对齐在网格上、一切规整；缺少一处有意的不平衡 |
| 海报像网页 / PPT | 用卡片和分区组织本该一眼读完的画面；文字小到远看成灰 |
| 杂乱 | 圆角、线宽、字体、色温各自为政 |
| 单薄、平淡 | 只设计了默认状态，操作缺少反馈，元素出现和消失时没有过渡 |
| 动画烦人 | 运动没有因果，多个元素争夺注意力，或动效与视觉方向不一致 |
| 3D 发假或糊成一团 | 光照平均；缺少雾和景深；粒子铺满全屏 |
| 图表难读 | 装饰压过数据；颜色编码了无意义的差别 |
