# 审计已有项目

适用于已有页面、界面或作品的检查、评审、优化与改版。**先读懂作品，再帮它变好。** 以用户目标和项目现有的设计系统、组件、字体及 token 为依据。需要补齐缺项时参考[网页视觉指南](floor-web-ui.md)。用户要求探索新方向时，再按[入口](../SKILL.md)使用方向卡。

## 0. 确认范围

- 按用户要的交付物决定怎么做。检查或评审交付报告。用户要求优化、修复或改版时，先确认问题，再直接做范围内的修改并汇报。
- 范围含糊时，以用户提供的页面、区域或作品为范围。把品牌色、字体、信息结构等明确约束作为判断依据。局部任务按受影响的区域、状态和断点检查。

## 1. 提取项目自己的系统

- **Token**。从 CSS 变量、主题文件、组件配置或设计规范里找颜色、字号、间距、圆角、阴影和动效时长。缺少明确规范时，对比多个同用途的实例，从实际样式归纳，并标明哪些是推断。
- **方向**。从作品、参考稿和已有规范判断它服务谁、希望传达什么、第一眼该看哪里。能指出具体物件、材料或版式来源就记下。线索不足时保留不确定性。
- **组件**。找出已有的按钮、卡片、表单等组件，区分有意设计的变体与同用途的样式漂移。

评价一致性时，对照项目自己的规则。例如项目统一用 8px 圆角，就保留 8px。可读性、操作和可访问性问题按实际影响及项目适用的标准判断。

## 2. 渲染和走查

- 按 [Codex 渲染指南](codex-rendering.md)打开实际效果。整页网页 / UI 审计默认看 1440 和 390 CSS 像素宽度，按项目支持的尺寸和任务要求调整。长页面看首屏、中段和末尾。其他媒介使用对应的实际渲染或导出预览。
- 涉及交互时，按[交互走查](floor-interaction.md#7-走查用用户的身份过一遍)验证范围内的主要流程和相关状态，包括键盘和窄屏。只评审时，用预览或测试环境复现会写入数据的步骤，缺少条件就记为未验证。截图、测量或复现步骤用来支撑具体问题。
- 只有用户给的截图时，视觉结论限于截图覆盖的画面。只有源码或 DOM 时，报告能从中确认的实现问题，视觉推断标为「疑似」。写明范围内尚未验证的页面、尺寸或状态。

## 3. 按四类检查

1. **硬伤**。检查遮挡、裁切、影响阅读的断行、意外的横向溢出、字体或图片加载失败、空白画布、不可见的键盘焦点及键盘无法完成的任务。补查[硬伤清单](../SKILL.md#第二遍硬伤必须做不算修改轮数)。

   网页文字可按适用的 WCAG 2.2 AA 条款核对对比度，普通文字通常至少 4.5:1，符合大字号定义的文字通常至少 3:1。15px 正文是本 skill 的默认值。44×44 CSS px 可作触控舒适度目标，也是 WCAG 2.2 AAA 增强目标尺寸条款的门槛，该条款同样有例外。核对 AA 时用 24×24 CSS px 门槛，并检查间距等例外。

   判断溢出时区分页面整体溢出与表格、地图等确需二维布局的区域。参见 W3C 的[文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[AA 目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[AAA 目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)和[重排](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)说明。
2. **系统一致性**。对照项目的 token 和组件，查同用途的近似色、字号、圆角与间距，同类组件的高度、内边距和图标线宽，以及强调色、动效时长和缓动是否仍有统一逻辑。
3. **层级与焦点**。判断第一眼落点是否服务主要任务，字号、明度和间距能否分清层级。对照[症状表](../SKILL.md#症状表卡住时查)定位问题。常见设计组合可作为线索，列入报告时说明它对当前目标或作品的具体影响。
4. **状态与细节**。查缺失的空、加载和错误状态，加载后跳动，操作无反馈，表单只用占位符当标签，出错后丢失输入，以及占位文字或灰色占位框残留。

检查类别帮助找问题，严重程度由实际影响决定。比如缺少错误状态通常是建议修，若用户因此无法恢复并完成主要任务，就归入必须修。

## 4. 按影响分级

| 级别 | 判断依据 | 例子 |
|---|---|---|
| 必须修 | 阻断关键操作、妨碍读取关键信息，或违反项目适用的可访问性要求 | 主要任务无法用键盘完成、关键信息被裁、对比度低于适用门槛 |
| 建议修 | 用户仍能完成任务，但操作有明显阻力，或同用途的设计偏离项目规则 | Token 漂移、同类按钮样式不一致、次要操作缺少反馈 |
| 可选 | 影响观感，基本使用仍成立 | 视觉焦点偏弱、装饰重复、局部气质不统一 |

证据不足的发现标为「疑似」，说明缺什么证据。能归到同一根因的问题合为一条，列出代表位置和受影响范围。

## 5. 修复和复查

- 先查共享 token 或组件的影响范围。能在本次范围内解决同一根因时，优先修源头。影响超出范围时，复用已有的正确 token 或组件变体做局部修复，或把共享改动列为建议。沿用项目的结构、命名和代码风格。
- 保留原有方向、字体家族、主色和信息结构。用户明确要求调整时，以用户指定的范围为准。
- 处理范围内已确认且可修复的「必须修」和「建议修」。任务包含视觉优化时，可选项最多做一轮，挑影响最大的一两处。每处改动对应报告里的一条发现。
- 修完重新渲染，复查修改位置、相邻区域和受影响的共享组件。交互修复重走对应流程。无法修复或复验的项目写明原因。

## 6. 交付报告

先用一两句概括作品的方向和最重要的问题，再按严重程度列发现。每条写清**位置、证据、影响和建议或已做的修复**。位置可以是页面、区域、组件或文件。尽量给出复现状态或视口宽度。

```text
整体概况

必须修（N 项）
- 位置与复现条件 · 观察到的现象 · 对用户的影响 · 建议或已做的修复

建议修（N 项）
- 同上。由同一原因引起的问题合并描述。

可选（N 项）
- 同上。保留最重要的一两项。

验证范围
- 已查看的页面、尺寸和状态，以及尚未验证的部分。
```

只做审计时，在报告里注明未改动文件。做了修复时，写明改动和复验结果。

## 交付前自查

- [ ] 已核对可获取的 token、组件和约束，区分直接证据与推断。
- [ ] 视觉结论有渲染依据。适用时走过主要交互流程，写明未验证范围。
- [ ] 每条发现有位置、影响和级别。证据不足的项目标为疑似。
- [ ] 所有修复都在授权范围内，可追溯到发现，并已复验或说明限制。
